## Общее описание

**Taiga** — комплексная система управления строительной компанией, предназначенная для:

- **Финансовый учёт:**
  - Учёт доходов и расходов
  - Ведение кассы с автоматическим расчётом остатков
  - История кассы с расчётом расходов за день
  - Автоматическая классификация расходов с обучением

- **Управление проектами:**
  - Управление клиентами и объектами
  - Опись работ по проектам
  - Отслеживание прогресса выполнения работ
  - Журнал ведения работ (ежедневный учёт)
  - Табель (автоматически формируется из журнала)

- **Справочники:**
  - Магазины/поставщики
  - Сотрудники
  - Категории расходов
  - Единицы измерения

- **Обучение системы:**
  - Автоматическое распознавание категорий расходов
  - Система правил классификации
  - Учебник правил записи расходов

## Принципы работы с данными

### Соответствие данных БД и Админки

**Критически важно:** Все данные, отображаемые в Админке, должны **100% соответствовать** данным в базе данных PostgreSQL.

**Правила:**
1. **Никаких заглушек или статических данных** — все данные загружаются динамически из БД через API
2. **Количество записей в БД = количество записей в Админке** — если в БД 10 записей, в Админке должно быть 10 записей
3. **Все значения полей** (суммы, даты, названия) должны точно соответствовать значениям в БД
4. **Записи создаются только при сохранении** — например, запись кассы создаётся только когда пользователь вводит фактическую сумму и нажимает "Принять" (✓)

### Примеры нарушений (запрещено):

❌ **Запрещено:** Отображать в Админке записи, которых нет в БД  
❌ **Запрещено:** Использовать статические HTML-заглушки вместо данных из БД  
❌ **Запрещено:** Автоматически создавать записи без действия пользователя (кроме системных случаев)  
❌ **Запрещено:** Отображать данные, которые не были сохранены в БД  
❌ **Запрещено:** Использовать липовые заглушки для клиентов, проектов, категорий и любых других справочников  
✅ **Обязательно:** Все клиенты, проекты, категории, магазины и другие справочники берутся ТОЛЬКО из базы данных PostgreSQL  

### Проверка соответствия

При разработке и тестировании необходимо проверять:
- Количество записей в БД совпадает с количеством в Админке
- Все значения полей соответствуют значениям в БД
- Нет "лишних" записей, которые не были сохранены в БД

## Система классификации расходов

### Цель системы

Автоматическое определение категории расхода на основе текстового описания, введённого пользователем "своими словами".

### Категории расходов

| Категория | Алиас | Описание |
|-----------|-------|----------|
| Материалы | Мат | Все строительные материалы |
| ФОТ | ФОТ | Фонд оплаты труда (зарплаты сотрудников). Подкатегория = выпадающий список работающих сотрудников |
| ТЗР | ТЗР | Транспортно-заготовительные расходы |
| Накладные | Накл | Накладные расходы (бензин, продукты и т.д.) |
| Инструменты | Инстр | Инструменты и оборудование |
| Расходные материалы | Расх | Расходные материалы (перчатки, диски и т.д.) |
| Маржа | Маржа | Личные деньги Макса (Барабанов М.В.). **ПОДКАТЕГОРИЯ ВСЕГДА = "Барабанов М.В."** (единственная подкатегория для Маржи). Требует обязательного комментария с описанием расхода |

**Важно:**
- **ФОТ:** При выборе категории "ФОТ" подкатегория становится выпадающим списком сотрудников со статусом "Работает" (из таблицы `employees`)
- **Маржа:** При выборе категории "Маржа" подкатегория **ВСЕГДА** автоматически подставляется как **"Барабанов М.В."** (это единственная подкатегория для категории Маржа). В комментарии указывается описание расхода (например, "массаж", "хозтовары (шапка, задярка) Лента" и т.д.)

### Правила классификации

Система использует правила из таблицы `expense_classification_rules` для определения категории.

#### Типы правил

1. **`employee`** - Имена сотрудников → категория "ФОТ"
2. **`keyword`** - Ключевые слова в тексте
3. **`material_pattern`** - Регулярные выражения для шаблонов материалов
4. **`pattern`** - Общие регулярные выражения

#### Приоритет правил

Правила применяются в порядке убывания приоритета (больше = выше). Первое совпавшее правило определяет категорию.

### Примеры классификации

#### Пример 1: Материал по шаблону размеров
```
Вход: "50х150х6000х6шт"
→ Правило: material_pattern '\d+[хxXХ]\d+[хxXХ]\d+'
→ Категория: Мат
```

#### Пример 2: Сотрудник
```
Вход: "Жура Даня"
→ Правило: employee 'Жура' или 'Даня'
→ Категория: ФОТ
```

#### Пример 3: Личные деньги Макса (Маржа)
```
Вход: "Барабанов М.В."
→ Правило: keyword 'Барабанов' или 'М.В.' или 'Макс'
→ Категория: Маржа
→ Подкатегория: автоматически "Барабанов М.В."
→ ⚠️ Требуется комментарий (обязательно!)
```

**Примечание:** "Барабанов М.В." больше НЕ относится к категории ФОТ. Все записи с именем Макса автоматически попадают в категорию "Маржа".

#### Пример 4: Транспорт
```
Вход: "Аренда Газели двое суток"
→ Правило: keyword 'Аренда' или 'Газель'
→ Категория: ТЗР
```

#### Пример 5: Накладные расходы
```
Вход: "Бензин для генератора"
→ Правило: keyword 'Бензин'
→ Категория: Накладные
```

### Особые случаи

#### Маржа (личные деньги Макса)

Когда категория определяется как **"Маржа"**, система **обязательно требует** заполнения поля "Комментарий". Это необходимо для ведения личной бухгалтерии Макса и отслеживания, на что были потрачены личные деньги.

**Примеры записей с Маржей:**
- "Макс (зубы)" - комментарий обязателен
- "Барабанов М.В. (Ольга)" - комментарий обязателен
- "М.В. ремонт" - комментарий обязателен

### Добавление новых правил

Новые правила добавляются в таблицу `expense_classification_rules`:

```sql
INSERT INTO taiga.expense_classification_rules 
(rule_type, pattern, category_id, requires_comment, priority, description)
VALUES 
('keyword', 'Новое ключевое слово', 
 (SELECT id FROM taiga.expense_categories WHERE alias = 'Мат'), 
 FALSE, 75, 'Описание правила');
```

### Справочник сотрудников

Все сотрудники хранятся в таблице `employees`:
- ФИО (фамилия, имя, отчество)
- Адреса (фактический и регистрации)
- Телефоны (массив номеров)
- Даты трудоустройства и увольнения
- **Статус** (автоматически обновляется): "Работает", "Уволен", "Не указан"
- Комментарии

**Автоматическое обновление статуса:**
- Если указана `hire_date` и нет `dismissal_date` → статус = "Работает"
- Если указана `dismissal_date` → статус = "Уволен"
- Триггер `trigger_update_employee_status` обновляет статус автоматически

**Важно:** 
- При выборе категории "ФОТ" в интерфейсе показывается выпадающий список только сотрудников со статусом "Работает"
- При добавлении нового сотрудника статус устанавливается автоматически на основе дат

## Журнал работ

Журнал работ — это ежедневный учёт выполненных работ по проекту. Доступен только внутри страницы проекта (вкладка "Журнал" на странице `client.html`).

### Структура записи журнала

Каждая запись в журнале содержит:
- **Дата** — дата выполнения работы
- **Время начала и окончания** — время начала и окончания работы (опционально)
- **Перерыв** — продолжительность перерыва в формате "чч:мм" (опционально)
- **Часы** — автоматически вычисляется из времени начала/окончания и перерыва
- **Сотрудники** — один или несколько сотрудников, выполнявших работу
- **Работа** — вид работы из описи работ проекта
- **Выполнено** — количество выполненной работы (в единицах измерения работы)
- **Примечания** — дополнительные комментарии

### Критические правила работы с журналом

⚠️ **СТРОГИЕ ОГРАНИЧЕНИЯ:**

1. **Работы ТОЛЬКО из описи работ проекта:**
   - При добавлении записи в журнал работа выбирается **строго** из списка работ проекта (`project_works`)
   - Нельзя вводить произвольный текст — только выбор из выпадающего списка
   - Если нужной работы нет в описи — сначала добавь её в раздел "Работы" проекта

2. **Сотрудники ТОЛЬКО из справочника:**
   - При добавлении записи в журнал сотрудники выбираются **строго** из справочника сотрудников (`employees`)
   - Нельзя вводить произвольные имена — только выбор через чекбоксы
   - Если нужного сотрудника нет в справочнике — сначала добавь его в раздел "Сотрудники"

3. **Автоматический пересчёт прогресса:**
   - При добавлении/изменении/удалении записи в журнале автоматически пересчитывается `completed_quantity` в соответствующей работе
   - Прогресс выполнения работы обновляется автоматически

4. **Остаток работ:**
   - В таблице журнала отображается остаток работ: `quantity - completed_quantity`
   - Остаток вычисляется автоматически на основе всех записей журнала для данной работы

### Табель

Табель формируется **автоматически** из журнала работ:
- Агрегация данных по сотрудникам и датам
- Суммирование часов за день для каждого сотрудника
- Доступен на вкладке "Табель" страницы проекта

### Примеры записей

**Пример 1: Работа одного сотрудника**
- Дата: 10.12.2025
- Время: 10:00 - 19:00
- Перерыв: 1:00
- Часы: 8 (автоматически)
- Сотрудники: Макс
- Работа: Стены - 50х100хх6000
- Выполнено: 2 шт

**Пример 2: Работа нескольких сотрудников**
- Дата: 08.12.2025
- Время: 10:00 - 19:00
- Перерыв: 1:00
- Часы: 8 (автоматически)
- Сотрудники: Макс, Жура
- Работа: Стены - 50х100хх6000
- Выполнено: 1 шт

## Установка и запуск

### Предварительные требования

- Node.js 14+
- PostgreSQL 12+
- Доступ к БД с правами создания схемы

### Настройка БД

1. Создать схему `taiga`:
```sql
CREATE SCHEMA IF NOT EXISTS taiga;
```

2. Выполнить скрипты создания таблиц из папки `БД/`:
   - `create_all.sql` - основная структура
   - `05_create_work_directories.sql` - справочники работ
   - `06_update_project_works_structure.sql` - обновление структуры работ
   - `18_create_expense_categories_with_aliases.sql` - категории расходов с алиасами
   - `19_create_employees_table.sql` - справочник сотрудников
   - `20_create_expense_classification_rules.sql` - правила классификации

### Запуск бэкенда

**Вариант 1: через PowerShell скрипт (рекомендуется):**
```powershell
cd E:\Forge\_projects\taiga\backend
.\RUN.ps1
```

**Вариант 2: вручную:**
```powershell
cd E:\Forge\_projects\taiga\backend
npm start
```

**Вариант 3: режим разработки (с автоперезагрузкой):**
```powershell
cd E:\Forge\_projects\taiga\backend
npm run dev
```

Бэкенд запускается на порту `3000`.  
**Проверка:** `http://localhost:3000/api/health`

### Запуск фронтенда (Админки)

```powershell
cd E:\Forge\_projects\taiga\frontend
python -m http.server 8000
```

Фронтенд доступен по адресу `http://localhost:8000/taiga.html`

⚠️ **Важно:** Сервер должен запускаться из папки `frontend`, чтобы файлы находились в корне!

## Система обучения классификации расходов

### Цель системы обучения

Автоматическое обучение системы на примерах пользователя для точного определения категорий расходов без ручного вмешательства.

### Процесс обучения

#### Этап 1: Получение чека с расходами
- Пользователь отправляет "чек" с расходами (текст, список позиций)
- Система получает список расходов для классификации

#### Этап 2: Определение категорий
- Система анализирует каждую позицию расхода
- Использует существующие правила из `expense_classification_rules`
- Определяет предполагаемую категорию для каждой позиции

#### Этап 3: Уточнение у пользователя
- **Система задаёт вопросы по одному** (не все сразу)
- Каждый вопрос имеет счётчик (1, 2, 3...)
- Система спрашивает: "Правильно ли определена категория?"
- Пользователь подтверждает или исправляет категорию
- **После подтверждения** система переходит к следующему вопросу
- При малейшем сомнении система задаёт уточняющие вопросы
- Обсуждение происходит последовательно, пока не будет достигнуто 100% подтверждение всех расходов

#### Этап 4: Совершенствование правил
- При обнаружении ошибки или нового случая система:
  - Анализирует, почему была ошибка
  - Создаёт новое правило или обновляет существующее
  - Сохраняет правило в `expense_classification_rules` для будущего использования

#### Этап 5: Добавление расходов в Админку
- После достижения **100% подтверждения** всех расходов от пользователя
- Система автоматически добавляет все расходы в Админку (таблица `expenses`)
- Каждый расход сохраняется с подтверждённой категорией и всеми данными

#### Этап 6: Критерий завершения обучения
- Обучение считается завершённым, когда система **3 раза подряд** определяет все расходы на **100%** без ошибок
- После этого система может работать автоматически

### Принципы обучения

1. **Активное уточнение:** При малейшем сомнении система задаёт вопросы
2. **Накопление правил:** Каждое новое правило сохраняется для будущего использования
3. **Приоритет точности:** Лучше спросить, чем ошибиться
4. **Итеративное улучшение:** Система учится на каждой ошибке

### API для обучения

- `GET /api/expense-classification/classify?text=...` - определение категории
- `POST /api/expense-classification/learn` - создание нового правила на основе выбора пользователя
- `GET /api/expense-classification/rules` - просмотр всех правил
- `DELETE /api/expense-classification/rules/:id` - удаление правила

### Пример процесса обучения

```
Пользователь: "Бетон М300, 2 куба"
Система: "Определяю категорию: Материалы (Мат). Правильно?"
Пользователь: "Да"
Система: "✅ Правило сохранено. При следующем упоминании 'Бетон' категория будет определена автоматически."

Пользователь: "Бензин для генератора"
Система: "Определяю категорию: Накладные (по слову 'Бензин'). Правильно?"
Пользователь: "Нет, это ТЗР"
Система: "❌ Исправляю. Создаю правило: 'Бензин для генератора' → ТЗР"
```
